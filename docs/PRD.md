# RuleForge 规则工坊 PRD（阶段0 需求底座）

> 版本：v0.1（2026-11-15）
> 状态：阶段0 定稿

---

## 1. 项目定位

**RuleForge 规则工坊**是面向业务人员、运营、人事、分析师、普通个人用户的**自然语言规则编排 Agent 工具**。
用户用大白话描述一条规则，系统将其翻译为结构化规则树，并在本地完成自检、冲突检测、仿真、影响分析等确定性处理，最终用通俗中文解释结果。

### 1.1 核心底层原则（红线，全程不变）

1. **LLM 只做两件事**：
   - ① 将用户自然语言翻译成符合规范的结构化规则树；
   - ② 把引擎输出的结构化结果翻译成通俗易懂的中文解释。
2. **确定性逻辑全自研**：冲突检测、沙箱仿真、规则树 Diff、判定推理**全部用自研代码实现**，不交给大模型判断，避免幻觉。

## 2. 目标用户与用户故事

| 角色 | 痛点 | 用户故事 |
| --- | --- | --- |
| 人事专员 | 写考勤/入离职规则要靠开发改代码 | 作为人事，我想说"迟到3次提醒主管"，系统就能生成规则并自检 |
| 运营/销售 | 促销规则互相打架、上线后才发现 | 作为运营，我想在改折扣前知道它和现有规则是否冲突 |
| 分析师 | 规则多了以后不知道改一条影响谁 | 作为分析师，我想知道改一条规则会影响哪些既有规则 |
| 普通个人 | 想给自己立生活小规则但没工具 | 作为个人，我想说"气温低于10度提醒我加衣"，系统帮我记住并提醒 |

### 用户故事（含验收口径）

- **US-01 翻译**：输入自然语言，输出结构化规则树（合法 JSON，字段符合 Schema）。
- **US-02 澄清**：输入不完整/歧义/非规则时，系统提示澄清问题，不硬凑。
- **US-03 自检**（阶段1）：单条规则做字段完整性/取值范围自检并给出中文说明。
- **US-04 冲突**（阶段2）：两条或多条规则间冲突被检出并中文解释。
- **US-05 解释**：引擎的任何结构化结果都能被翻译成通俗中文。

## 3. 一期 MVP 与二期迭代划分

> 阶段编号：阶段0/1 由项目既定流程定义；阶段2 起为本 PRD 提出的路线，待评审确认。

### 3.1 一期 MVP（核心闭环：建规则 → 自检 → 冲突 → 用起来）

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| **阶段0 需求底座** | Schema 定稿、PRD、API/SQLite/日志、NL→规则翻译 + 校验重试、测试用例库 | 当前阶段 |
| **阶段1 规则基础管理与单规则自检** | 规则 CRUD、单条规则字段自检（完整性/枚举/取值范围） | 既定下一阶段 |
| **阶段2 多规则冲突检测** | 冲突引擎（动作冲突/优先级冲突/条件重叠/互斥），输出 `Conflict` 结构体 | 使用已冻结的冲突结构体 |

### 3.2 二期迭代（增强能力）

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| **阶段3 沙箱仿真执行** | 用自研代码对规则做样本数据仿真，输出执行轨迹 | 不交给 LLM 判断 |
| **阶段4 规则树 Diff 与变更影响分析** | 规则版本 Diff、改一条规则的影响面分析 | 自研比对算法 |
| **阶段5 可视化流程图与导出** | 规则可视化、JSON/图片/文档导出 | UI 增强 |

### 3.3 明确的非目标（本阶段不做，避免超前）

多条规则冲突检测引擎、沙箱仿真、版本 Diff、变更影响分析、可视化流程图、导出功能。

## 4. 功能需求（阶段0 范围）

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 自然语言 → 结构化规则 | 10 条样例 ≥8 条一次输出合法 JSON；格式错误自动重试 ≤2 次 |
| FR-02 | 规则 Schema 冻结 | 字段定稿，`extra=forbid` 防新增 |
| FR-03 | Claude API 接入 | 本地可一键调用，异常捕获 + 超时处理 |
| FR-04 | SQLite 存储 | 规则增删查 + 解析日志读写正常 |
| FR-05 | 日志模块 | 控制台 + 滚动文件双输出 |
| FR-06 | 测试用例库 | 覆盖人事/销售/个人生活 + 正常/缺陷/冲突 |
| FR-07 | 澄清机制 | 输入不完整/歧义/非规则时返回 clarification 而非硬凑 |

## 5. 异常场景

| 场景 | 表现 | 处理策略 |
| --- | --- | --- |
| 未配置 API Key | 解析不可用 | 启动时明确提示；离线自检/单测仍可用 |
| API 鉴权失败（401） | 抛 `AuthenticationError` | 转译 `LLMError`，提示检查 Key |
| 请求限流（429） | 抛 `RateLimitError` | 转译 `LLMError`，提示稍后重试 |
| 请求超时 | 抛 `APITimeoutError` | 转译 `LLMError`，配置超时 120s |
| 网络中断 | 抛 `APIConnectionError` | 转译 `LLMError` |
| LLM 输出非 JSON | 解析失败 | 自动重试（≤2 次），附带错误反馈 |
| LLM 输出 JSON 但不符合 Schema | 校验失败 | 自动重试（≤2 次），附带错误反馈 |
| 输入为空 | 无法解析 | 直接返回失败，不调用 API |
| 输入不完整/歧义/非规则 | LLM 返回 clarification | 展示澄清问题，不硬凑规则 |
| LLM 拒绝（refusal） | `stop_reason=refusal` | 转译 `LLMError` |
| 数据库文件缺失 | 首次启动 | 自动建表（幂等） |

## 6. 风险清单

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| LLM 翻译不稳定（字段/枚举漂移） | 解析成功率波动 | Schema 冻结 + `extra=forbid` + 格式错误重试 + 测试用例回归 |
| LLM 幻觉编造条件/动作 | 规则错误 | 红线约束 LLM 只翻译；澄清机制；阶段1 自检兜底 |
| 依赖 LLM 做确定性判断 | 结果不可复现 | 冲突/仿真/Diff 全部自研，LLM 不参与 |
| API 成本/限流 | 批量场景成本高 | 提示词缓存友好（稳定前缀）；后续可切批量/低价模型 |
| Schema 过早冻结导致后续需求不适配 | 返工 | 阶段0 已充分讨论冻结；演进需走升版本+回归流程 |
| SQLite 并发写入 | 多用户冲突 | 单机本地优先；后续可迁移，连接用 `with` 短事务 |
| 阶段边界失控（超前开发） | 返工/验收混乱 | 严格按阶段交付，完成即停，等验收 |

## 7. 非功能需求

- **本地一键启动**：`pip install -r requirements.txt` + 配置 `.env` 即可运行。
- **轻量**：不引入重型外部服务（数据库用 SQLite，无消息队列/微服务）。
- **模块化**：每层独立目录、每个核心能力独立文件，预留单元测试入口。
- **可观测**：LLM 调用全部记录日志与原始输出，便于排查。
- **中文注释**：函数写明入参/出参。
